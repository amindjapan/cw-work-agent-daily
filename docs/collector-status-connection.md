# Collector status connection

The status view separates a completed workflow observation, stored collection material, and a verified successful collection. A stopped workflow does not replace the stored summary or add a collection date. The legacy summary containing thirteen HTTP 403 results is failed material; it does not establish a last successful collection. Unproven success remains `UNKNOWN`.

## Public inputs

`collector-status/attempts/` contains explicitly reviewed observations of the two already completed public workflow runs. Each record identifies the repository, workflow path, run and attempt, source commit, public run/job links, workflow timestamps, fixed diagnostics, and original step results. The collector's own start and finish remain null because those times were not recorded. Later metadata persistence does not change the original snapshot, commit or publication steps from `SKIPPED` to success. The hash binds canonical fields; it does not authenticate a GitHub response or prove raw log contents.

The initial adapter accepts stopped daily-workflow observations only. It reads supplied bytes or objects and never retrieves logs. Conflicting records with the same identity, changed hashes and ambiguous ordering are rejected. Latest selection uses workflow start time and attempt, rather than file order or import time.

`public-patrol/latest.json` is the disconnected public export, `UNAVAILABLE`, with unknown counts. No Return text or private application or hold history is imported. The initial structured opportunity contract supports CrowdWorks; other services are explicitly unsupported. Condition matching and security review remain separate, and neither authorizes an application.

## Shared offline builder

`build-collector-site.js` reads explicit local inputs once, validates them, and passes memory snapshots to the overview composer. It does not import the collector or scraper, invoke Git, call APIs or publish anything. Only validated public fields are rendered. The current source summary and existing date archives retain their bytes and SHA256 hashes. The status-only builder does not create a date archive or increment DAY. Invalid or overlapping inputs fail before writing output. The final public-artifact projector validates the staging directory again and rebuilds HTML and Markdown from the strict public JSON contract. An explicitly supplied reconstruction manifest adds a separately validated `reconstruction.json` disclosure; it does not modify the saved summary or archives.

Both the daily workflow's publication preparation and the manual status-view workflow use this builder and projector. The daily collection command, stop gate, snapshot commit, permissions and schedule are unchanged. The status-view workflow is main-only and manual, with read-only contents permission, no persisted checkout credentials, and the existing Pages deployment permissions. It has no collection command, repository write, log retrieval, retry or schedule.

## Explicit Git reconstruction release mode

An exact backup of the previously served Pages artifact has not been obtained. The known historical artifact download returned 404 and the artifact collection was empty. The reconstruction does not repair that evidence gap: original artifact bytes and original delivery-file hashes remain unavailable. Do not retry the old ZIP download or use another connection, permission or route to obtain it as part of this release.

The owner has explicitly accepted that a Git reconstruction may differ from the old delivery, and authorized normal main integration and one status-view publication under this separate mode. This is not an exact-backup waiver disguised as successful preservation. The original `verify-preserved-site.js` verifier and its `collector_preservation` contract remain unchanged. The connection workflows invoke the new `reconstructed-baseline.js` verifier with a different manifest kind and explicit paths; they do not pass reconstructed material to the old artifact verifier or silently fall back between modes.

The reviewed input is `collector-preservation/reconstructed/site/` with an external `collector-preservation/reconstructed/manifest.json`. Its `collector_git_reconstruction` schema records `inputCommit`, `sourceCodeBaseCommit`, `reconstructedAt`, source repository paths, baseline paths, actual Git blob SHA1 values, byte lengths and SHA256 values. The source records bind `collector-data/latest.json` and each existing dated source JSON to its reconstructed counterpart. Exact commit IDs and hashes come from that reviewed manifest; they must not be inferred from the publication time or substituted from another checkout.

The accepted manifest records input commit `b6cad17aeac34681e94114d8b25df2e44e4908f8`, source-code baseline commit `36eaa1df684628d0ba33118094b26daf39a9e593`, and reconstruction time `2026-10-30T04:56:54.296Z`. It binds 67 source JSON inputs, including 66 dated archives. Its 72 hashed baseline files plus the manifest mirror form a 73-file reconstructed site. The external manifest, existing baseline bytes and their hashes remain fixed; a later daily collection must not regenerate or overwrite this accepted return point.

The manifest explicitly declares `originalArtifact.availability: UNAVAILABLE`, `originalArtifact.exactMatch: NOT_VERIFIED`, and missing `ORIGINAL_ARTIFACT_BYTES`, `ORIGINAL_DELIVERY_FILE_HASHES` and `ORIGINAL_COLLECTOR_TIMESTAMPS`. `reconstructedAt` is the reconstruction time, not a collector start, collection completion, old publication time or verified success. `reconstruction.json` mirrors the strict manifest in both the baseline and the final artifact. It is excluded from the manifest's own file-hash list to avoid a circular hash. Provenance is `GIT_RECONSTRUCTION`, not proof of original artifact equality or authenticated log contents. All source material must be reviewed public data; private operational sources are not inputs.

`reconstruction.json.files` is the immutable 72-file hash index of the accepted restoration baseline, not a hash index of the entire latest delivery whose `asOf` and rendered state may change; verify that delivery separately through its run, uploaded artifact and available public read.

Existing tests and the reconstruction checks must succeed before build, upload and deploy. The builder receives the manifest through `--reconstruction` and each publisher supplies an explicit `--reconstruction-mode` matching the final verifier's `--mode`. The verifier checks the fixed baseline before building and the final artifact after projection.

For compatibility, programmatic builder callers that omit `reconstructionMode` default to `status-only`; an unknown value or `null` is rejected before output. The publishers do not depend on that default: their mode is explicit at both build and final verification.

In `status-only` mode, the input and published `latest.json` must retain the baseline source bytes, and the dated archive path set and hashes must match the reconstruction exactly. No status-only reconstruction step creates a new collection date, changes a source JSON file or increments DAY.

In `daily` mode, the current successful collection summary is a separate input from the immutable reconstructed baseline. It may differ from the baseline's `latest.json`, and a normal collection may supply new date archives. Existing reconstructed archives cannot be dropped or changed. The builder preserves the bytes of the supplied current summary; the disclosure continues to identify the fixed reconstruction's provenance and return point, not to claim that the new daily summary was part of that reconstruction. Requiring a daily summary to equal the old baseline latest would reject legitimate updates and is not the daily contract. The fixed baseline and its source-input bindings are verified separately and are never rewritten to make a changed latest appear original.

Both publishers retain the existing Pages concurrency group. They compare the checked-out commit against current main before building and immediately before deployment; a stale checkout fails. The daily publisher uses actual Git HEAD, which includes its existing successful snapshot commit. The collection command, access-stop gate, schedule, permissions and snapshot steps before publication preparation are unchanged. The status-only publisher has no collection command, schedule, repository write or log retrieval. Authorization for this release does not authorize new collection, automatic retries or additional status-view dispatches.

Release still requires successful existing test-only CI and normal main integration; no protection or review gate is bypassed. After the one authorized status-view publication, independently check the Actions result, uploaded artifact and served public page, including the reconstruction disclosure and unchanged source hashes. An uploaded artifact alone does not establish publication success, and a failed page read must remain unverified rather than being replaced by an inferred result.

## Validation and rollback

Artificial fixtures cover stopped searches and details, unknown timestamps, ordering and identity conflicts, strict projection, disconnected patrol, original preservation checks, explicit reconstruction provenance, missing disclosure, manifest and source hash mismatches, links, unchanged summary/archive hashes, and the common build-to-artifact path. No external job site is contacted. The test-only pull-request workflow runs Node 22, syntax checks and the complete test suite; it does not deploy or collect.

Retain this reviewed reconstructed site, its manifest, source inputs and input commit as the accepted return point. It is not the previously served Pages artifact. Rollback is a separately reviewed source revert and, if required and authorized, re-publication of this reconstructed baseline through the existing Pages path. A source revert alone does not restore a served site. This release does not establish that the old exact delivery can be restored, and the one publication authorization is not an automatic authorization for a later rollback deployment. Do not fetch the old ZIP, expand permissions, bypass protections or collect new data to recover.
